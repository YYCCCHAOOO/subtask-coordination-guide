# 子任务协调指南

一套平台无关的协作协议，用于将复杂目标拆分为边界清晰的工作单元，协调执行过程，并综合形成可信结果。

这套协议将长期任务线程、临时代理和串行工作流视为可互换的执行器，并要求它们遵守统一的任务包与结果包契约。协调者始终对最终目标、依赖关系、写入边界、冲突、决策和任务闭环负责。

## 为什么需要这套协议

复杂工作往往不是失败在单项任务内部，而是失败在任务交接处。常见问题包括：

- 两个执行器同时修改同一文件或记录；
- 下游任务把未经验证的假设当成事实；
- 提示中缺少验收标准或禁止事项；
- 冗长的返回内容掩盖了阻塞项和验证失败；
- 因为所有执行器都结束运行，就误判父目标已经完成。

本指南要求在工作开始前明确责任和交接规则。

## 适用场景

当目标涉及以下一种或多种需要时，可以使用本协议：

- 清晰隔离不同任务的上下文；
- 开展独立的研究、实现或审查；
- 按依赖关系组织并行工作；
- 严格控制写入权；
- 设置明确的用户决策门；
- 形成紧凑且可审计的结果回传；
- 综合多个领域或多个代码仓库的工作。

对于只有一个负责人和一个输出的小型线性任务，简单清单通常已经足够。

## 必备的协调说明

在以下字段明确之前，不要分发任务：

1. `final_goal`：一个可观察、可验收的最终状态。
2. `coordinator_scope`：协调者负责什么，以及不得亲自执行什么。
3. `subtasks`：边界明确的工作单元，包含责任、排除范围、输入、输出、验收检查、依赖关系和写入范围。
4. `ordering`：依赖波次，或者任务可以并行的明确理由。
5. `conflict_policy`：共享文件、共享标识符、矛盾结论和决策门的处理规则。
6. `executor_profile`：已配置的模型、推理级别、工具，以及任何有理由的例外。
7. `return_contract`：协调者继续工作所需的精确、紧凑的返回格式。

## 选择执行器

应根据责任和生命周期选择执行方式，而不是根据代理技术选择：

- **长期任务线程**：适合重复性工作、大型独立上下文或需要用户持续跟进的任务。
- **临时代理**：适合当前目标中的有限实现、审计、检索或独立批评。
- **串行工作流**：适合并发会增加冲突风险，或者没有独立执行器可用的工作。

不要仅仅为了逃避推理而创建新任务。只有当责任边界和回传边界确实有意义时，才应新建任务。

## 工作流程

### 1. 规范化目标

将请求重写为：

- 一个最终目标；
- 明确的非目标；
- 可测量的验收标准；
- 决策权限；
- 稳定标识符和规范输入位置。

### 2. 设计边界明确的子任务

为每个子任务指定：

- 一个唯一且可问责的责任；
- 明确的排除范围；
- 完成该责任所需的最少上下文；
- 互不重叠的写入权，或者只读角色；
- 可测量的输出与验证；
- 依赖关系和返回目标。

如果两个子任务可能修改同一文件、注册表、数据库行或实体标识符，不要让它们并发运行。应指定唯一写入者，并将另一个任务设为只读任务或依赖任务。

### 3. 构建优化后的提示

先写最终目标，然后依次写明：

1. 子任务的唯一责任；
2. 最少背景和规范输入；
3. 必须遵守的规则或策略文件；
4. 允许写入的范围和禁止事项；
5. 依赖关系和当前波次；
6. 验收检查；
7. 执行器配置和有理由的例外；
8. 精确的结果格式和返回目标。

优先引用稳定路径和标识符，不要复制大段源材料。应要求每个执行器自行读取所属领域的规则，不要把整个项目复制到每个提示中。

### 4. 按依赖波次分发

只分发依赖条件已经满足的子任务。只有在写入范围和决策权限互不冲突时，才可以并发执行同一波次。后续波次应保持等待状态，不要要求它们猜测尚未产生的上游结果。

### 5. 审查返回结果

只接受以下结果状态：

- `done`
- `partial`
- `blocked`
- `needs_decision`

审查证据、已变更资产、验证结果、边界合规情况、未解决风险和请求的下一步动作。

不要静默合并互相矛盾的结论。应记录竞争性主张、各自证据、受影响的下游任务，以及协调者的处理决定或需要用户裁决的问题。

### 6. 继续或关闭

更新依赖状态，并且只向下一波任务传递新增且必要的上下文。只有当所有必需输出均通过验收检查，而且剩余风险已经明确时，才能关闭最终目标。

## 冲突锁

| 锁 | 规则 |
| --- | --- |
| `write_lock` | 同一时点只能有一个子任务拥有可变目标的写入权。 |
| `id_lock` | 一个标识符命名空间只能有一个主体负责创建或重命名标识符。 |
| `decision_lock` | 执行器可以提出建议，但不得代替协调者或用户作出决定。 |
| `evidence_lock` | 候选项、推断或未验证路径不得被升级为事实。 |
| `sequence_lock` | 下游任务可以准备结构，但在依赖任务完成前不得正式应用变更。 |

字段值应保持简洁。通过规范输入位置引用材料，不要复制大段源内容。

## 边界规则

- 协调者负责组织和综合。除非明确重新分配，否则专业实现仍由对应执行器负责。
- 未经协调者批准，子任务不得扩大最终目标、创建同级任务或修改其他子任务的范围。
- 子任务不得把依赖条件中的假设当成事实。
- 长期任务可以在自己的领域内协调更小的子任务，但必须向父任务返回一份综合结果。
- 原始工具日志和长篇笔记应保留在执行器任务或规范项目中，回传时只提供紧凑结论和原始产物位置。
- 缺少权限、高风险写入、外部动作和改变范围的选择必须向协调者或用户升级。

## 隐私与发布检查清单

在分享任务包、结果包、提示、截图或代码仓库前：

- 用角色标签替换个人姓名和内部系统名称；
- 用规范占位符替换本地绝对路径；
- 删除凭据、令牌、一次性代码、账号标识符和私有网址；
- 将服务商特定的模型和推理设置参数化；
- 删除私有项目名称、数据集、稳定标识符和未公开发现；
- 检查暂存差异，而不仅是工作副本；
- 在完整发布范围内扫描密钥和环境特定标记；
- 确认所有被引用的文件均已包含在发布范围内或可公开访问；
- 确认仓库可见性与目标受众相符。

## 完成标准

协调者的最终报告应说明：

- 最终目标状态；
- 已完成、部分完成和受阻的子任务；
- 已接受的输出及其规范位置；
- 验证证据；
- 未解决的冲突和决策负责人；
- 边界合规情况；
- 建议的下一波工作。

绝不能仅仅因为所有执行器都结束了各自回合，就宣布父目标已经完成。

## 简明示例

假设一次发布需要实现、文档和安全审查：

1. 协调者定义发布结果，并负责最终集成。
2. 实现子任务独占源代码写入范围。
3. 文档子任务只能修改指南，并且必须依赖已经冻结的接口。
4. 安全子任务保持只读，在实现完成后可以与文档审查并行开展。
5. 协调者比较全部结果包、解决冲突、运行集成检查，并且只有在验收标准通过后才关闭发布任务。

这套协议的价值不在于使用了多少代理，而在于责任、证据、顺序和交接是否清晰。
